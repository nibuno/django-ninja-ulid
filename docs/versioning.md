# バージョンと互換性方針

決定日：2026-10-18。初回の通常リリースを`0.1.0`とする。版の確定と、公開の実施は別の判断として扱う。

## 公開APIと仕様

互換性を管理する公開シンボルは、次の3つである。

```python
from django_ninja_ulid import ApiULID
from django_ninja_ulid.orm import create_ulid_response_schema, related_ids
```

対象は、READMEに記載した入力形式・正規化・出力形式、必須・null・省略、関連ID、拒否する設定と例外型、公開関数の引数である。検証エラーの文章全体、内部の補助関数、定数は固定しない。`__all__`に含めない名前へ直接アクセスできても、公開APIとしては扱わない。

## 0.xでの変更の分類

| 変更 | 版の上げ方 | 例 |
|---|---|---|
| 既存の仕様を使うコードの変更が必要になる変更 | マイナー版 | 入力の受理条件、null・省略、応答の形式、関数の引数の変更 |
| 既存の仕様を保つ不具合修正 | パッチ版 | 文書に記載した挙動への修正、内部処理の修正 |
| 公開API・依存条件を変えない文書やメタデータの修正 | パッチ版 | README、PyPIの説明、ドキュメントリンクの更新 |
| 公開機能の追加 | マイナー版 | 新しい公開関数や応答形式の追加 |

破壊的変更は、たとえば`0.1.x`から`0.2.0`へ上げる。互換性を保つ修正は`0.1.0`から`0.1.1`へ上げる。版の表記は[PEP 440](https://peps.python.org/pep-0440/)に従う。

変更内容と移行方法はCHANGELOGへ記録する。非推奨化を経られる変更は、削除前に利用者へ案内する。非推奨期間の一律の長さや、固定したサポート年数は現時点では約束しない。

依存の更新や対応するPython・DBの終了も、利用者が導入・更新できるかに影響する変更として扱う。対応範囲を狭める場合はマイナー版で通知し、対応表・依存指定・CIを同時に更新する。依存更新の確認頻度と対応終了の基準は、公開計画の別の判断事項に残す。

## 公開済みの配布物

同じ版で異なる内容を再公開しない。修正が必要な場合は新しい版を用意する。TestPyPIで検証した配布物をPyPIへ送る際は、同じwheel・sdistとSHA256を使い、途中で作り直さない。[リリース手順](releasing.md)
